# Implementation Plan: ghost-voice

## Overview

Build the ghost voice in four stages, one task at a time, each ending at a Checkpoint. First the baseline is recorded and the legacy output of the offline engine is frozen, before any edit. Then `coffin_core` gets the two facts, the mood templates, the catalog and engine change, the property tests, the replacement of the expired AI guard (design F1) and the README section (Checkpoint A, with a Chrome run). Then the pure Hauntagotchi domain (`VoiceTrigger`, `VoiceSnapshot`, `VoicePolicy`, `VoiceSeed`) with unit and property tests and a source rule (Checkpoint B, with a Chrome run). Then the UI logic (mood mapping, request builder, `HomeController` counters, `VoiceController`) with a scripted session test (Checkpoint C). Then `VoicePanel`, the `HomeScreen` and `HauntagotchiApp` wiring (Checkpoint D). The last tasks build for web and verify the whole repository.

All code is Dart in Flutter, following `design.md`. Paths are relative to the repo root `/Users/ranmanlabs/Documents/Kiroween/coffin`. Tests use `flutter_test` and `glados`. Every task is required. No test task is optional.

Never create a file outside the repository, including `/tmp`. Write no scratch files, and use no shell redirection to any file. Do not create files that are not listed in a task.

- Files under `packages/coffin_core/lib/src/ai/` follow the existing source rules: no `package:flutter`, no `dart:math`, no `dart:io`, no `DateTime.now`, no URL or key words, at most one public class per file, imports of sibling files only (plus `seeded_random.dart` for the engine). Every public member in `coffin_core` carries a doc comment. One public class per file, `snake_case.dart`, `final` wherever possible, `flutter_lints` clean.
- Mood copy rules (Requirements 4 and 2): one line, at most 80 characters after filling the slots with the worst case (40-character name, streak 1000000), printable ASCII or the ellipsis U+2026 only (no emoji), no gore, no shame, no word of `TextRules.bannedWords`, streak only as `{streakCount:day/days}`, only in `thriving` and `content`, at most one name slot per template.
- `glados` exports its own `expect`, `group` and `test`, so test files `hide` the clashing names from the glados import, as the existing property tests do. Tag each property test with `// Feature: ghost-voice, Property N: <title>` and `// Validates: Requirements ...`.
- Use only web-safe glados generators, as the existing files do: `anyIntBetween`, `any.simple`, `combineN`, `choose`, `either`, `oneOf`, `always`, `bool`, `map`, `nullable`, and strings built from a fixed alphabet by `any.simple`. Never use `any.int`, `any.intInRange`, `any.list`, `any.listWithLengthInRange`, glados string generators, `uint*` generators or `double` generators. Keep every generated integer below 2^32. Hauntagotchi property tests must pass `test/source_rules/generator_rules_test.dart`.
- Run counts: 300 runs for every property of this feature. Every property file counts its runs with a counter incremented in the body, and a plain `test(...)` after the glados test in the same group asserts `runs > 0 && runs == numRuns`.
- Widget tests use explicit `pump(Duration)` calls and never `pumpAndSettle` on a looping widget. Tests render with the Ahem font, so never assert glyph shapes. No golden tests.
- Chrome commands (tasks 2.10 and 3.8): `CHROME_EXECUTABLE="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" flutter test --platform chrome <files>`, run in the package named by the task. Pure tests must give the same result on the VM and in Chrome.
- Long commands (`flutter test --platform chrome`, `flutter build web`, full `flutter test`) use an explicit timeout of 1800000 ms. Use `flutter test` without watch flags. Do not start dev servers.
- Do not mark a task done until `flutter test` passes in every package the task touched.
- HARD STOP conditions (stop, report the exact difference, wait for the user, never edit an expected value, a count or an existing test to make a run pass): a pubspec, `pubspec.lock`, `apps/graveyard` or `tool` file differs from the task 1.1 baseline; an existing test fails; a legacy baseline value of task 2.1 differs after the engine change; a pinned seed value differs on the VM and in Chrome; a test outside the two allowed edit lists above needs an edit.
